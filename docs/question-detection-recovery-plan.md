# 会议问题识别故障隔离与恢复方案

2026-11-21 · 已实现并完成候选版工程验证，未替换安装版 · 适用于实时会议和录音导入

**目标：一条问题找不到发言依据时，同批有依据的问题照常进入查证，下一段发言继续识别。失败项必须有去处；用户不用守着“重试”按钮。** 原话校验和现有查证权限继续生效。

## 事故依据与范围

一次录音导入暴露了相同批次的问题校验错误阻塞后续识别的缺陷。诊断时音频和转写已保存，部分新发言未继续处理；模型返回的依据无法匹配所引的新发言，修正一次后仍不合格，错误为 `quote_not_in_new_segment`。隔离测试在实时识别路径上复现了相同后果：新转写保存成功，但识别没有再次启动。具体会议名称与现场数据只留在本机私有诊断资料中。

此次修改针对问题发现、恢复和状态展示。录音采集、转写模型、已完成的查证结果不需要重做。验收分别判断两件事：程序是否处理了所有输入，以及模型是否识别出了真正有价值的问题。扫描完毕只能证明前者。

## 识别与恢复规则

| 遇到的情况 | 当前批次怎么处理 | 接下来怎么做 |
|---|---|---|
| 问题列表可读，个别条目的字段或引文无效 | 从解析阶段逐条校验，通过的条目立即提交。保留失败项的任务编号、原因和来源范围 | 新发言优先；后台带必要上下文，仅纠正该失败项一次。仍无法确认则标记“待核对”，不触发搜索 |
| 整份响应无法解析，或错误引用无法定位到发言 | 保存本次输入范围和版本；若已有可确认的合格项，保留其提交记录 | 将未确认范围拆成较小窗口，保留相邻发言供消解指代；限定尝试次数。持续失败的范围可人工查看 |
| 同批输出达到动作上限 | 按**过滤前**的输出保守判断是否还有未返回的问题。例如上限为 4，返回 4 条、仅 3 条合格，仍须登记续扫 | 续扫时携带已建问题、已处理条目和待补项；无进展或达到轮次上限时，把该范围列为待核对，不阻塞后续发言 |
| 网络超时、限流或服务不可用 | 暂时性网络错误沿用现有有限退避；按服务端提示和现有预算执行。引文不匹配不做相同请求的定时重放 | 相同服务持续失败时合并积压、限制请求，显示识别受阻；凭证或权限错误须处理后恢复。录音和转写保持各自状态 |
| 用户暂停、结束会议、撤回权限或更正发言 | 暂停和结束后不再调度补偿；新旧结果都须重新校验会议、问题和发言版本 | 显式恢复后处理剩余任务；过期结果不写入。发言更正后以新版本重评，删除会议时同步清理任务 |

**原话编号在首版实现。** 本机给本批新发言的连续原文片段分配短编号，记录发言 ID、版本和文本位置。模型选择编号，程序从转写回填原话；旧发言可用于理解上下文，但不能单独作为新问题的依据。可借鉴回答阶段已有的编号回填机制，分段则按会议发言设计，不能照搬网页引文的最短长度而遗漏“为什么？”这样的短问句。编号存在只证明原话真实，不证明它支持问题标题；用人工标注样本检查“引用真实但答非所问”的情况。

## 持久化与进度

1. **区分扫描进度和未完成工作。** 主扫描位置只表示“此前输入已作出处理安排”。SQLite 另外记录待纠正项、待续扫范围和待人工核对项。某范围只要仍有上述任务，就不能显示“全部完成”。有效空结果可以结案；修正时把原有问题改成空列表，不能算修正成功。
2. **一次提交三个结果。** 在同一 SQLite 事务中保存合格动作、未完成任务和主扫描位置。任一写入失败就全部回滚。提交时再检查来源版本；可归属单项的版本冲突只影响该项，会议权限失效或存储故障则中止整个事务。只有写入成功的问题才进入查证队列。
3. **补偿有独立提交入口。** 现有入口会忽略主扫描位置之前的批次，不能直接用来提交旧任务。首次保存任务时分配稳定编号，重试沿用该编号；问题创建或修订与任务完成标记在同一事务内完成。重复回调、并发点击和重启恢复不能重复建题或重复触发查证。扩大范围重扫时还要对照已提交动作和既有问题，避免模型改写标题后重复创建；也不能仅按发言编号合并同一句里的两个独立问题。
4. **调度与操作可见。** 新发言使用实时通道，补偿使用有并发和次数上限的后台通道；长会持续有新输入时，后台任务仍须获得执行机会。任务记录保存引用、范围、状态、尝试数及下次执行条件，避免在诊断日志复制整段转写。重启后恢复任务记录，遵守现有暂停策略，不能把“记录已恢复”等同于“获准重新调用模型”。

## 实施顺序与交付

| 步骤 | 主要改动位置 | 完成条件 |
|---|---|---|
| 1. 建立回归用例，调整识别协议 | `tests/test_workbench_grounded_detection.py`、`live/workbench_contracts.py`、`live/workbench_runtime.py` | 在现有实现复现阻塞。识别专用解析器能保留合格项和原始条目数，并支持原话编号；回答与纪要沿用原有严格校验 |
| 2. 实现可靠提交与后台补偿 | `live/workbench.py`、`live/workbench_runtime.py` | 原子写入、重复提交、饱和续扫、转写修订和重启恢复测试通过；补偿任务无法越过暂停或权限检查 |
| 3. 接通进度、操作与旧会议恢复 | `live/workbench_api.py`、`static/workbench.js`、`templates/workbench.html` | 局部失败显示“新发言识别中，1 项待核对”，可定位音频时间和原因，单项重试只处理该项。整体服务不可用时单独提示 |
| 4. 候选版验证后发布 | 测试数据库、会议回放、候选桌面包 | 核实打包后端与测试版本一致；通过下列验收后再替换安装版。停用新版时保留未完成任务，不让不认识新扫描进度的旧调度器直接接管 |

**本场旧会议的恢复方式：** 从保存的已提交位置之后读取实际剩余转写，沿用已有问题和查证结果，无需重新导入录音。旧记录没有保存被拒绝的引文，因此恢复单位是未处理范围，不能凭错误码重建当时的候选问题。先在会议副本上验证；升级不应自动重跑全部历史会议，也不应改变已暂停会议的状态。

## 发布验收

| 场景 | 必须观察到的结果 |
|---|---|
| 同批 A 正确、B 引文错误，随后收到 C | 无人点击重试，A、C 各进入查证一次；B 单独补齐或可见地停在“待核对”。转写连续保存 |
| 字段类型错、非法编号、跨版本引用、整份 JSON 损坏 | 能归属单项的错误不拖累其他项；无法归属的输入范围仍可回查。任何无可靠依据的问题都不自动发起查证 |
| 输出上限为 4，返回 4 条但仅 3 条合格，原文另有第 5 问 | 在有确定期望输出的测试中，第 5 问通过续扫被识别；前三条不重复，失败项没有消失 |
| 提交前后分别中断、重复回调、同一任务被再次领取 | 事务要么都写入，要么都未写入；恢复后无遗漏，已完成任务不产生第二个问题或第二次查证 |
| 后台任务运行期间暂停、结束、撤权或更正转写 | 旧结果不覆盖新状态，后台不擅自恢复；重新授权或显式恢复后，合法的未完成任务可继续 |
| 本场 300 段回放及实时输入 | 分别验证完整回放和从事故检查点恢复；逐段核对当时剩余的 126 段是否有处理记录或待核对范围。另做实时新发言测试，记录新问题出现延时、额外模型调用数、重复题、漏题及引用错误。漏题和错引用以人工标注片段为基准，不以扫描进度代替 |

实施结果见 [2026-11-21 验收报告](verification/2026-11-21-question-detection-recovery.md)。步骤 1–3 已完成，已生成 build 40 候选包并验证打包后端、浏览器操作及会议副本回放。正式安装替换未执行；人工标注的语义召回与错引用评估、真实长会收音验证仍未完成，不能用工程检查通过代替这些验收。

降级时不能直接让旧程序接管新版数据库。`tools/prepare_detection_rollback.py` 会保留新版原库，另行导出暂停的副本；将未确认范围保守回退到可重扫位置，并要求显式核对、重试。旧版本本身不认识 `detection_protocol` 标记，不能把该标记当作旧程序会遵守的保护。
